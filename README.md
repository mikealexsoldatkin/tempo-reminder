# Forge-приложение: напоминание в Slack о незалогированном времени

Приложение сверяет **явно выбранный список пользователей Jira** с worklog'ами Tempo и шлёт **DM в Slack**
тем, у кого нет записей **за каждый** из последних N рабочих дней. Всё настраивается через UI —
**env-переменные не используются**.

## Страница настроек

Jira → **Настройки** → **Приложения** → **Tempo Reminders**. Доступна только администраторам Jira
(резолверы дополнительно проверяют право `ADMINISTER` — adminPage лишь прячет пункт меню).

Порядок вкладок повторяет порядок первой настройки: **Access → Users → Check parameters →
Holidays → Vacations → Run check**. Без доступов бессмысленно заводить людей, без людей — крутить
параметры проверки.

Над вкладками висит **сводка готовности** (`ReadinessBanner`): она собирает в одном месте всё, что
мешает приложению работать — неподключённый Slack и незаданный токен Tempo, пустой список людей,
пустые расписания, включённый календарь отпусков без ссылки, отслеживаемых без единого менеджера. Красная — не уйдёт ничего,
жёлтая — работает, но часть задуманного молчит. Пока всё в порядке, баннера нет. Раньше про каждую
из этих нехваток говорила только своя вкладка, и администратор, добавивший полсотни человек,
узнавал о неработающей рассылке по её отсутствию.

**Сообщения о результате действия гаснут сами** (`useTransientMessage`, ~8 секунд): «Token saved»,
«Holiday added», «Run times saved». Висящее сообщение перестаёт быть отчётом о нажатии кнопки и
начинает читаться как описание текущего состояния — а про состояние говорят лозенги у полей и
сводка готовности, и они никуда не деваются. **Ошибки не гаснут никогда**: по ним нужно что-то
делать, и исчезнувшая причина отказа оставляет администратора с неработающим приложением и без
объяснений. Их перезаписывает только следующее действие.

**Всё время на странице — в UTC и с подписью**: `2026-08-15 14:03 UTC` (`formatInstant` в
`src/frontend/formatTime.js`). Расписания, окно проверки и списки дней приходят с бэкенда в UTC, а
метки времени (старт прогона, обновление токена) рисовались через `toLocaleString()` в зоне
браузера — и в строке «время прогона · окно проверки» соседние числа оказывались из разных поясов,
так что разница в три часа читалась как расхождение данных. Зона названа в самой строке: без
подписи «14:03» неотличимо от местного времени.

### 1. Вкладка «Access»

Двум внешним системам приложение представляется по-разному, и вкладка это показывает.

- **Slack — кнопка «Connect Slack»**. Открывает в соседней вкладке экран согласия Slack: выбрать
  workspace, нажать Allow. Токен приложение получает и сохраняет само — ни создавать Slack-приложение,
  ни собирать scope'ы, ни копировать `xoxb-…` администратору не нужно. Как это устроено —
  в разделе [«Подключение Slack»](#подключение-slack). Пока идёт подключение, страница опрашивает
  бэкенд и подхватывает результат сама: он приезжает не ответом на действие в UI, а через веб-триггер.
  Рядом — **Disconnect**: отзывает токен в Slack (`auth.revoke`) и удаляет его у себя.
  Поля для ручного ввода `xoxb-…` на вкладке нет: предлагать двадцать шагов рядом с одной кнопкой
  незачем. Токен, вставленный руками в прежних версиях, продолжает работать — такое подключение
  подписано как «вставлен руками» и заменяется тем же нажатием «Connect Slack».
- **Tempo API token** — password-поле: у Tempo подключения по кнопке нет, OAuth-приложение там
  регистрирует у себя сам клиент, и это больше шагов, чем выпуск токена. Где его взять —
  в разделе [«Где взять токены»](#где-взять-токены).
- Любое значение — и полученное по OAuth, и вставленное руками — кладётся в секретное хранилище
  Forge (`kvs.setSecret`) и наружу **никогда не возвращается**: UI видит только «set / not set»,
  последние 4 символа и дату обновления. Вставленный токен сохраняется по Enter, не целясь в кнопку,
  а **Remove** спрашивает подтверждение: значение не читается обратно ни приложением, ни UI, так что
  удалённый токен восстановить нечем — только выпускать новый.
- **Test connection** — дёргает Tempo и Slack `auth.test` текущими токенами.
- Если Slack ответит на прогоне «токена больше нет» (`token_revoked`, `invalid_auth`,
  `account_inactive`), подключение помечается разорванным: вкладка и сводка готовности говорят
  «Slack rejected the connection» и зовут подключиться заново. Событий Slack приложение не слушает —
  для этого нужен постоянно доступный сервер, — поэтому узнаёт об этом только по коду ошибки; без
  пометки администратор видел бы «подключено к Acme Corp» и молчащую рассылку одновременно.

### 2. Вкладка «Users»
Вместо прежнего `getProjectPeople()` список отслеживаемых людей задаётся вручную:

- **Поиск по имени** — вводите First + Last name (Jira ищет и по email), отмечаете нужных
  галочками и добавляете **батчем**.
- **Добавить участников проекта** — по ключу проекта подтягивает людей из **собственных ролей
  проекта**, то есть ровно то, что видно в Project settings → People. Общие (инстансные) роли
  игнорируются. Ещё не отслеживаемые отмечаются автоматически, в таблице видно, из какой роли
  пришёл человек.

Обе формы открываются во всплывающем окне. Постоянным блоком над списками они не стоят: нужны они
редко, а места занимали столько, что таблицы уходили под сгиб. Кнопки живут в ряду действий своей
таблицы — там же, где «Remove selected» и «Clear selection»:

- **Managers** — «Add managers», поиск по имени. Целым проектом менеджеров не назначают, поэтому
  второй кнопки здесь нет.
- **Tracked users** — «Add users» (поиск по имени) и «Add project members».

Поиск в обоих окнах запускается и по Enter, и кнопкой; таблица результатов сортируется по клику на
заголовок — в том числе по колонкам «Tracked» и «Manager», чтобы отделить новых от уже заведённых.

Куда попадёт отмеченный, решает кнопка, которой открыли окно, а не выбор внутри него: в окне одно
действие и называется оно просто **«Add»**. Списки при этом не связаны — один и тот же человек может
быть и отслеживаемым, и менеджером, просто добавляют его двумя заходами, каждый от своей таблицы;
где человек уже есть, видно лозенгами в таблице результатов. Состояние поиска живёт до закрытия
окна, добавленные люди попадают в таблицу сразу.

Таблиц на вкладке две, **Managers первой**: колонки менеджеров в Tracked users выбирают именно из
неё, и пустой список делает их нередактируемыми.

Обе таблицы устроены одинаково:

- **Сортировка** — по клику на заголовок колонки (имя, email, Slack). По умолчанию список идёт по
  имени, а не в порядке добавления.
- **Поиск по таблице** — поле над ней, по имени и email. Появляется от шести строк: на пяти оно
  только мешает. Отметки, сделанные до фильтра, сохраняются.
- **Галочка в шапке** отмечает всё видимое (при включённом фильтре — всё найденное) и она же
  снимает отметки; полусостояние показывает, что отмечена часть.
- **Удаление спрашивает подтверждение** и перечисляет в окне поимённо, кого именно удаляет. Это не
  вежливость: отметки живут поперёк страниц пагинации, так что часть выделенного в момент нажатия
  на экране не видна. Для менеджеров окно отдельно проговаривает каскад — удалённый исчезает из
  колонок получателей у всех сотрудников, и обратно эти колонки никто не соберёт.

> **Две особенности UI Kit, которые видно в коде.** `Textfield` не принимает `onKeyDown` (его
> пропсы — `onChange`, `onBlur`, `onFocus` и ничего больше), поэтому везде, где нужен Enter — оба
> поиска, оба поля токенов, адрес календаря, — поле с кнопкой завёрнуты в `Form` с
> `onSubmit`, а кнопка помечена `type="submit"`. Соседние кнопки в такой форме обязаны нести
> `type="button"`, иначе «Remove» отправляет форму вместо своего действия. Сортировка `DynamicTable`
> берёт значение не из `content` (элементы UI Kit ей сравнивать нечем), а из **`key` ячейки строки**,
> поэтому у сортируемых колонок ключ ячейки — это само значение, а не имя колонки.

#### Tracked users

Единственный список людей, за которыми следит приложение. Быть в нём значит «проверяем в Tempo и
пишем лично, если время не залогировано». Кому уходят сообщения **о** человеке, задают две
независимые колонки менеджеров:

| Колонка | Что уходит |
| --- | --- |
| **Managers who get the basic report** | дайджест «не отчитался» со списком пропущенных дней |
| **Managers who get the detailed report** | разбор worklog'ов день за днём, задачами и описаниями |

Наборы не связаны: можно заполнить любой, оба или ни одного — на личное напоминание самому
сотруднику это не влияет. Выбирать можно только из таблицы Managers; удаление менеджера снимает
его сразу из обоих наборов у всех сотрудников.

> Раньше это были **два независимых списка**, Tracked users и Detailed tracking users, и человек мог
> быть только во втором — тогда его worklog'и разбирались в отчёт менеджеру, но сам он напоминаний
> не получал. При переезде (`mergeLegacyDetailedUsers` в `store.js`, разовая, по ключу
> `detailed-users`) такие люди становятся обычными отслеживаемыми и начинают получать напоминания:
> одна таблица не может означать «следим» и «не следим» одновременно.

Детальный отчёт — это **разбор дня за днём**, что списано в Tempo по каждой задаче:

```
2026-08-10:
- 5.5h - ABC-123: [Development] Переписал импортёр
- 1h - ABC-140: [Meetings] Планирование спринта
2026-08-11:
- no time entries
2026-08-12:
- Independence Day — a holiday
```

`[Type of work]` в скобках — это **work attribute** записи в Tempo (в ответе API он приходит в
`attributes.values`). Атрибутов у записи может быть несколько — тогда они перечисляются через
запятую; если их нет вовсе, скобок в строке не будет. Пустое описание worklog'а заменяется
заголовком задачи. Первым в строке идёт списанное время в часах: дробное округляется до сотых
и пишется без хвостовых нулей (`1.5h`, `0.25h`, `8h`).

Устройство:

- **Пока колонка пуста, отчёт не собирается вовсе** — ни запроса в Tempo, ни сообщения. Именно
  непустой набор получателей и означает «следить за этим человеком глубоко».
- **Одно сообщение — один сотрудник.** Сшивать нескольких в одно письмо значило бы отправить
  менеджеру простыню, в которой ничего не найти.
- **Окно — целиком «Working days to check»**, без скидки на «Acceptable days of delay»: менеджер,
  который смотрит человека глубоко, хочет видеть и сегодняшний день. Пустой день оправдывают только
  выходной, праздник и календарь отпусков, и причина печатается прямо под датой — пустая строка
  неотличима от «приложение недосчиталось записей».
- **Расписание — то же, что у «Manager run times»**, отдельного поля нет. Но по выходным детальные
  отчёты не уходят, даже если галочка «Don't run the scheduled check on weekends» снята. Ручной
  запуск с вкладки «Run check» это правило игнорирует, как и остальные.

> **Про email.** Slack ищется по email, а приложению видны только профильные поля с видимостью
> **«Anyone»**. Email обычно стоит «Only people in your organization»: коллега видит его в профиле,
> приложение — нет. Поэтому адреса берутся через Email API (`/rest/api/3/user/email/bulk`), который
> отдаёт их независимо от видимости; он требует scope `read:email-address:jira` и в Forge работает
> **только через `asApp()`**. Если адреса нет и там, в таблице будет «set an email» — впишите вручную.
> Найденный Slack-id кэшируется, чтобы не звать `users.lookupByEmail` каждый прогон.

### 3. Вкладка «Check parameters»
- Параметры проверки:
  - **Working days to check** — всё окно: последние N рабочих дней, включая сегодняшний;
  - **Acceptable days of delay** — сколько самых свежих рабочих дней окна прощаем (время за них
    ещё могут не успеть занести). Значение всегда меньше окна, чтобы хотя бы один день спрашивался.
- **Логика проверки:** время должно быть залогировано **за каждый** рабочий день окна по отдельности,
  а не «хоть за какой-нибудь». Спрашиваемые дни = окно минус допустимая задержка: при 5 и 1 прогон
  проверяет 4 рабочих дня до сегодняшнего. Достаточно одного дня без записей, чтобы человеку ушло
  напоминание; в сообщение подставляется список именно пропущенных дней.
- Ещё параметры: времена запуска двух рассылок и четыре шаблона сообщений (сотруднику,
  менеджеру-дайджест, детальный отчёт, менеджеру «все отчитались») с плейсхолдерами `{name}`,
  `{from}`, `{to}`, `{days}`, `{missing}`, `{missingCount}`, `{count}`, `{list}`, `{user}`,
  `{report}`. Пропуск выходных и праздников переехал на вкладку «Holidays».
- **Кнопки «Save» здесь нет.** Как и на вкладках Holidays и Vacations, изменение применяется само —
  в момент потери фокуса полем, а не на каждое нажатие клавиши: сохранять на `onChange` значило бы
  слать резолверу запрос на букву и пытаться разобрать «09:» как время посреди набора. Рядом с
  заголовком висит состояние: «all changes saved», «unsaved — click outside the field» или спиннер.
  Сохранения выстраиваются в очередь — `saveSettings` читает и пишет настройки целиком, и два
  параллельных запроса при быстром переходе между полями затёрли бы друг друга.
- **Нормализация проговаривается вслух.** Бэкенд приводит «9, 15:30» к «09:00, 15:30» и прижимает
  числа к границам; в форму всегда возвращается то, что реально сохранилось, а расхождение с
  введённым показывается строкой «Saved, with adjustments: …». Молча подменённое значение — ровно
  тот случай, когда администратор уверен, что настроил одно, а работает другое. Так же видно и
  побочное зажатие: уменьшили окно — вместе с ним подвинулась и допустимая задержка.
- Четыре поля — окно, задержка и оба расписания — стоят одним рядом в четыре колонки.

> **Про вёрстку колонок в UI Kit.** Колонки здесь сделаны так: `Inline` с `grow="fill"` и
> `xcss({ width: '100%', flexGrow: 1 })` на каждой обёртке. Ни `shouldWrap`, ни `flexBasis` тут не работают: при переносе строки каждый элемент
> требует свои `width: 100%` и ряд рассыпается в столбик, а `flexBasis` до вёрстки просто не
> доезжает — `xcss` пропускает только белый список свойств (`flexGrow`, `width`, `minWidth`,
> `maxWidth`, отступы, цвета…), и `flexBasis` в него не входит. Нижнюю границу колонки, если она
> нужна, держит `minWidth`.
- **Manager run times** — одно расписание на всё, что уходит менеджерам: дайджесты, «все
  отчитались» и детальные отчёты. Отдельного поля под последние нет намеренно — они и есть часть
  менеджерской рассылки, просто не уходят по выходным.
- В шаблоне детального отчёта `{name}` — имя **получателя** (менеджера), `{user}` — тот, о ком
  отчёт, `{report}` — сам разбор по дням. Подстановка идёт за один проход, поэтому `{days}`,
  случайно оказавшийся в описании worklog'а, числом не станет.

### 4. Вкладка «Holidays»
Сверху — две галочки, определяющие, какие дни считаются нерабочими: **«Don't run the scheduled check
on weekends»** и **«Take the holiday calendar into account»**. Обе сохраняются сразу, без отдельной
кнопки. С выключенным календарём список ниже ни на что не влияет — праздники становятся обычными
рабочими днями.

Сам календарь: праздник — не рабочий день, поэтому в окно проверки он не попадает и планового
прогона в этот день нет.

Праздники хранятся **правилами**, а не датами, иначе календарь пришлось бы переписывать каждый год:

| Тип | Что задаёт | Пример |
| --- | --- | --- |
| `fixed` | одно и то же число каждый год | 1 января, 25 декабря |
| `nth-weekday` | N-й день недели месяца (N < 0 — с конца) плюс сдвиг в днях | последний понедельник мая |

Сдвиг нужен для дней, привязанных к другому празднику: пятница после Дня благодарения — это
«4-й четверг ноября + 1 день», а **не** «4-я пятница ноября»: в годы, где 1 ноября приходится на
пятницу (например, 2030-й), это разные даты.

Набор по умолчанию: Новый год (1 января), православное Рождество (7 января), День Победы (9 мая),
Memorial Day (последний понедельник мая), Independence Day (4 июля), Labor Day (первый понедельник
сентября), Thanksgiving (4-й четверг ноября) и следующий за ним день, католическое Рождество
(25 декабря). Кнопка **«Restore defaults»** возвращает этот список — с подтверждением, потому что
она заменяет календарь целиком: добавленные вручную правила при этом исчезают, и вернуть их можно
только набрав заново.

Форма добавления живёт в **модальном окне** — кнопка «Add a holiday» над таблицей. На вкладке она
занимала экран под действие, которое делают несколько раз за всё время. Ошибка правила показывается
внутри окна и введённое не стирает: закрывать окно, чтобы прочитать причину и набрать всё заново, —
худший из возможных ответов на опечатку. После успеха окно закрывается, поля очищаются, а тип
правила остаётся: праздники обычно заводят пачкой одного вида.

### 5. Вкладка «Vacations»

Отпуск — это **не долг**: день, который человек провёл в отпуске, вычёркивается из его пропущенных,
поэтому о нём не спрашивают ни самого сотрудника, ни его менеджера. Если отпуск закрыл все
спрашиваемые дни, человек не получит ничего и в дайджест менеджера не попадёт.

Логика **подневная**, а не «человек в отпуске — выключаем целиком». Вернувшийся из двухнедельного
отпуска не получит претензию за дни своего отсутствия, но за уже отработанные дни окна — получит.
В отличие от праздника, отпуск не меняет ни само окно рабочих дней, ни решение «запускать ли прогон
сегодня»: он персональный.

Две галочки, обе сохраняются сразу:

- **«Take the vacation calendar into account»** — учитывать календарь вообще;
- **«Don’t message a person while they are on leave…»** — если человек в отпуске **сегодня**, но за
  более старые дни окна долг есть, DM придерживается до его возвращения. В дайджест менеджеру он
  при этом попадает, чтобы дни не потерялись.

**Доступ к календарю.** Приложение читает корпоративный календарь отпусков по ссылке
**«Secret address in iCal format»** (Google Calendar → нужный календарь → Settings → Integrate
calendar). Ни OAuth, ни сервисного аккаунта, ни проекта в GCP не требуется — что важно, если
доступа к GCP у администратора нет. Ссылка сама себе пароль, поэтому лежит в том же секретном
хранилище, что и токены, и наружу не отдаётся: в UI видно только id календаря и дату обновления.
Обращение с полем такое же, как с токенами: Enter сохраняет, **Remove** спрашивает подтверждение —
прочитать адрес обратно нельзя, только скопировать заново из настроек календаря.

> **Про задержку.** Этот фид Google отдаёт из кэша, так что отпуск, добавленный HR только что,
> приложение увидит не сразу (обычно в пределах нескольких часов). Для отпусков, которые заводят
> заранее, это приемлемо; если однажды станет мешать, менять придётся только
> `vacationCalendar.js` — остальное от способа доступа не зависит.

**Как события связываются с людьми.** Событие считается отпуском, если в его заголовке встретилось
имя отслеживаемого сотрудника: `[vacation] Aleksandr Bugrov`. Тег в начале роли не играет — в этом
календаре любое событие означает, что человека нет на работе. Сравнение не различает регистр,
диакритику и пунктуацию, но идёт **по границам слов**, иначе «Ann Lee» находилась бы внутри
«Joann Leeson». Учитываются только события **на весь день**; события со временем и повторяющиеся
(`RRULE`) в отпуска не идут — последние считаются отдельно и попадают в предупреждение, чтобы не
пропасть молча.

Если в календаре человека пишут иначе, чем в Jira (никнейм, другой порядок слов, кириллица),
впишите это написание в колонку **«Name in the vacation calendar»** на вкладке Users; несколько
вариантов — через запятую.

**Test connection** отвечает не только «читается / не читается»: он показывает ближайшие события с
пометкой, кто из отслеживаемых в них узнан, и отдельным списком — заголовки, не сматчившиеся ни с
кем. Это единственный способ заметить разошедшееся написание имени до того, как напоминание уйдёт
человеку в отпуске.

**Если календарь не ответил**, прогон не останавливается: отпуска просто не учитываются, а причина
попадает в отчёт предупреждением. Остаться без напоминаний из-за недоступности Google хуже, чем
один раз дёрнуть отпускника; молчать об этом нельзя, потому что «отпусков нет» иначе не отличить
от «календарь не прочитался».

### 6. Вкладка «Run check»
Кнопка **«Start check»** запускает тот же прогон, что и расписание, но немедленно и в обход
`scheduledTrigger`. Ограничения «выходной» и «раз в день» на ручной запуск не действуют. Перед отправкой
показывается подтверждение — уходят **реальные** сообщения в Slack. Ниже — отчёт последнего прогона
(кто залогировал, кому ушло напоминание, кто был в отпуске, где ошибка), а под ним — что ушло
менеджерам: дайджесты и детальные отчёты строкой на пару «сотрудник — получатель».

Прогон выполняется не в резолвере, а в **очереди** (`@forge/events`): у резолвера лимит ~10 секунд,
а Tempo и Slack приходится опрашивать с паузами. Поэтому UI поллит статус, пока job в работе.

**Ход прогона видно на экране.** Консьюмер отмечает в статусе фазу и «сделано из скольких»
(`setRunProgress` в `store.js`, `RUN_PHASE` в `reminder.js`): чтение worklog'ов, календарь отпусков,
напоминания сотрудникам, дайджесты менеджерам, детальные отчёты. Страница показывает это строкой и
полосой — «Messaging tracked users: 12 of 50» вместо безымянного «running…», по которому зависший
прогон неотличим от долгого. Пока счёта нет (очередь, первые секунды), полоса неопределённая.
Отметки пишутся не чаще раза в 2 секунды (UI опрашивает статус раз в 3), поверх состояния
`running` и только его: закончившийся прогон поздней отметкой не воскресить. Побочный полезный
эффект — живой прогон не считается зависшим: `updatedAt` сдвигается на каждой отметке, так что
признаком зависания становится молчание, а не длительность.

Сообщение о постановке в очередь исчезает, когда прогон закончился: под ним уже лежит отчёт этого
самого прогона, и рядом с ним «The check has been queued» читается как «идёт ещё один».

## Где взять токены

Slack подключается кнопкой и токена не требует — см. [«Подключение Slack»](#подключение-slack).
Токен остался один, Tempo; он вводится на вкладке **«Access»** страницы настроек и попадает
в секретное хранилище Forge (`kvs.setSecret`). Обратно в UI он не отдаётся: видно только
«set / not set», последние 4 символа и дату обновления. После сохранения нажмите
**Test connection** — приложение дёрнет Tempo и Slack `auth.test` текущими значениями.

### Tempo API token

1. В Jira откройте **Apps → Tempo**, затем в левом меню Tempo — **Settings** (шестерёнка внизу).
2. Раздел **API integration** → кнопка **New Token**.
3. Заполните:
   - **Name** — понятное имя, например `Tempo Reminder (Forge)`;
   - **Expiration** — срок жизни токена (после истечения прогон начнёт падать с ошибкой
     `Couldn't fetch worklogs from Tempo`, токен придётся выпустить заново);
   - **Scope / доступ** — достаточно **чтения worklog'ов** (`View worklogs` / read-only).
     Права на запись приложению не нужны.
4. Нажмите **Create** и **сразу скопируйте значение** — Tempo показывает токен один раз.
5. Вставьте его в поле **Tempo API token** и нажмите **Save**.

> Токен работает от имени того, кто его создал: этот человек должен видеть worklog'и **всех**
> отслеживаемых сотрудников (обычно это Tempo-администратор). Иначе часть людей окажется
> «не отчитавшимися» просто потому, что их записи не видны токену. По той же причине токен,
> выпущенный увольняющимся сотрудником, лучше перевыпустить заранее.

> Бот Slack пишет только в личку (DM), приглашать его в каналы не нужно. Чтобы найти человека
> в Slack, приложению нужен его **email** — тот же адрес, что в Jira. Если адреса нет, в таблице
> отслеживаемых будет «set an email»: впишите его вручную, иначе сотрудник получит статус
> `no email` и сообщение ему не уйдёт.

## Подключение Slack

Администратор Jira нажимает **Connect Slack**, выбирает workspace, жмёт **Allow** — всё. Ни
создания Slack-приложения, ни сборки scope'ов, ни копирования `xoxb-…`: раньше на это уходило
полтора десятка шагов в чужой консоли, и половина обращений в поддержку была про них.

### Как это устроено

```
страница настроек ──startSlackConnect──► nonce в KVS, ссылка на согласие
        │
        └─ router.open ─► slack.com: выбрать workspace, Allow
                              │
                              └─ redirect_uri ─► статическая страница-переходник
                                                     │
                                                     └─ ?code&state ─► веб-триггер этой установки
                                                                          │
                                                       oauth.v2.access ◄──┘
                                                                          │
                                                        токен в kvs.setSecret, страница «готово»
```

Три решения, которые стоит объяснить.

**Почему не встроенный OAuth Forge** (`providers.auth` + `api.asUser().withProvider(...)`). Внешние
провайдеры Forge работают только в пользовательском контексте, а вся рассылка идёт из
`scheduledTrigger` и консьюмера очереди, где пользователя в сессии нет: `asApp()` с внешними
провайдерами не поддерживается. Кнопка бы работала, ночной прогон — нет. Поэтому токен приложение
получает само и кладёт туда же, куда клали вставленный руками, — в секретное хранилище Forge;
`reminder.js` и `slack.js` разницы не замечают.

**Зачем статическая страница-переходник.** Slack принимает только заранее зарегистрированные
`redirect_uri`, а адрес веб-триггера Forge свой у каждой установки
(`https://<installation-id>.webtrigger.atlassian.app/public/<token>`) — вписать их все в настройки
Slack-приложения нельзя. Поэтому Slack всегда возвращает браузер на один и тот же статический
адрес, а куда идти дальше, приезжает в `state`. Страница (`docs/slack-callback/index.html`) ничего
не хранит, никуда не ходит и не знает `client_secret`: она проверяет, что адрес назначения — это
веб-триггер Forge, и делает `location.replace`. Обмен кода на токен выполняет уже само приложение,
поэтому токен не проходит через чужой сервер и хостинга с состоянием не требуется.

**Чем защищён анонимный веб-триггер.** Платформа его не аутентифицирует — знающий адрес может позвать
его с любыми параметрами. Единственное доказательство, что подключение начал администратор этой
Jira, — одноразовый `nonce`: он рождается в резолвере (`startSlackConnect`), лежит в KVS десять
минут и гасится при первой же проверке, до похода в Slack. Подписывать `state` нечем и незачем:
секрет, которым можно было бы подписать, и есть тот же nonce.

### Что настраивается один раз, при сборке приложения

1. **Slack-приложение** на <https://api.slack.com/apps>. Быстрее всего — **Create New App → From a
   manifest** и вставить `docs/slack-app-manifest.json`, заменив в нём `redirect_urls` на адрес
   опубликованной страницы-переходника. Что там задано и почему — в комментарии внутри файла;
   вручную то же самое настраивается так:
   - **OAuth & Permissions → Bot Token Scopes**: `chat:write`, `users:read`, `users:read.email` —
     ровно то, что нужно для «найти по email и написать в личку». `im:write` не нужен:
     `chat.postMessage` с `channel=U…` открывает личку сам. Лишние scope'ы режут на ревью Slack
     в первую очередь;
   - **Redirect URLs**: адрес опубликованной страницы-переходника (по одному на окружение, если
     dev и production живут раздельно);
   - **Manage Distribution → Activate Public Distribution**: без этого приложение ставится только
     в свой workspace. Листинга в Slack Marketplace для установки в чужие workspace **не требуется** —
     он отдельный шаг и нужен для витрины, а не для OAuth.
2. **Страница-переходник**: `docs/slack-callback/index.html` публикуется на любой статический хостинг
   (GitHub Pages из папки `docs/`, Cloudflare Pages, S3). Сервер не нужен.
3. **Переменные окружения Forge** — они одни на все установки и задаются вендором, а не клиентом:
   ```bash
   forge variables set          SLACK_CLIENT_ID     1234567890.0987654321
   forge variables set --encrypt SLACK_CLIENT_SECRET <client secret>
   forge variables set          SLACK_REDIRECT_URI  https://<домен>/slack-callback/
   forge deploy   # переменные подхватываются только следующим деплоем
   ```
   Без них подключиться нельзя вообще: вкладка честно говорит, что реквизитов Slack-приложения
   у этой сборки нет, и зовёт задать переменные — вводить токен руками страница больше не предлагает.

### Установки, где токен вставляли руками

Подключение по кнопке — единственный путь в UI, но старые установки не ломаются: вставленный
раньше `xoxb-…` лежит в том же секретном хранилище и работает, пока его не заменят. Вкладка
подписывает такое подключение как «вставлен руками» и зовёт нажать **Connect Slack** — после этого
приложение получит собственный токен, а прежний останется висеть в Slack-приложении, из которого
его брали, и его стоит отозвать там же.

## Установка и деплой

```bash
npm install
forge variables set          SLACK_CLIENT_ID     <client id>       # см. «Подключение Slack»
forge variables set --encrypt SLACK_CLIENT_SECRET <client secret>
forge variables set          SLACK_REDIRECT_URI  https://<домен>/slack-callback/
forge deploy
forge install     # выбрать Jira и указать сайт
```

Если приложение уже установлено, а в `manifest.yml` добавились scope'ы или модули, после
`forge deploy` обязателен **`forge install --upgrade`**: новые права требуют подтверждения
администратором, и до апгрейда приложение работает со старым набором scope'ов. Веб-триггер
`slack-oauth-callback` появляется тем же апгрейдом — без него кнопка «Connect Slack» не сможет
получить адрес возврата.

Переменные окружения — единственное, что задаётся через CLI, и они про сборку, а не про клиента:
это реквизиты Slack-приложения вендора, одни на все установки. Токен Tempo, подключение Slack и
список пользователей задаются только на странице настроек после установки.

## Как проверить

- **Из UI** — кнопка «Start check», результат сразу в отчёте под ней.
- **Локально** — `npm test` (расчёт окна рабочих дней), `forge lint`, `forge tunnel` + `forge logs`.

## Известные подводные камни

1. **Нет cron** у scheduledTrigger — только `fiveMinute | hour | day | week`. Стоит `day`; выходные,
   праздники и окно рабочих дней считаются в коде (`src/backend/workdays.js`, `holidays.js`), защита
   от повторной рассылки — настройка «не повторять за день». Время запуска — UTC, и даты праздников
   разворачиваются в том же UTC.
2. **Приложение не видит email в профиле.** Forge-приложениям доступны только поля с видимостью
   «Anyone», поэтому `/user/search` и `/user/bulk` возвращают `emailAddress` далеко не всегда —
   даже когда вы сами видите адрес в профиле сотрудника. Читаются адреса через Email API
   (`/user/email/bulk`, scope `read:email-address:jira`, только `asApp()`). Scope в статусе Beta.
3. **Egress**: любой внешний домен обязан быть в `permissions.external.fetch.backend`, иначе `fetch`
   отклонят (`REQUEST_EGRESS_ALLOWLIST_ERR`). `api.tempo.io` и `slack.com` уже прописаны.
4. **Rate limits**: Tempo режет на ~5 req/s — worklog'и тянутся одним пагинированным запросом на всё
   окно с ретраями на 429/5xx; между вызовами Slack стоят паузы.
5. **Размер значения в KVS** ограничен, поэтому отчёт о прогоне обрезается до 300 строк
   (сначала ошибки и пропуски); полный список — в `forge logs`.
6. `scheduledTrigger` стартует примерно через 5 минут после первого деплоя/установки.
7. **`@forge/events` v2+ сменил контракт консьюмера**: вместо `resolver: {function, method}` в
   манифесте пишется `function:`, а хендлер — обычная `export async function handler(event)`,
   где тело лежит в `event.body`. Старая форма **всё ещё проходит `forge lint`**, но рантайм
   отклоняет `queue.push()` с `400 Bad Request` без пояснений.
8. **Участники проекта берутся из ролей, а не из `/user/assignable/search`.** Тот эндпоинт отдаёт
   всех, у кого есть право «Assignable User»; если оно выдано на «Any logged in user», возвращается
   весь инстанс. При этом `/project/{key}/role` возвращает и общие роли инстанса, поэтому берём
   только те, у которых `scope.type === 'PROJECT'` (собственные роли проекта). Если своих ролей нет
   вовсе — это company-managed проект, где все роли общие и при этом и есть People, и тогда берём
   все. Группы внутри ролей разворачиваются через устаревший `/rest/api/3/group?expand=users`:
   актуальный `/rest/api/3/group/member` требует scope `manage:jira-configuration` — право на изменение
   конфигурации Jira, непропорциональное для read-only приложения. Если Atlassian уберёт устаревший
   эндпоинт, альтернатива — добавить этот scope и перейти на `group/member`.
9. `"type": "module"` в package.json заставляет webpack считать наш код строгим ESM, из-за чего
   default-импорт CJS-пакета связывается со всем `module.exports`. Поэтому резолверы собираются
   через именованный `makeResolver()`, а не через `new Resolver()` (иначе — `out is not a constructor`).
10. **В worklog'е Tempo нет ключа задачи** — только числовой `issue.id` Jira. Для детального отчёта
    ключи (и заголовки, чтобы подставить их вместо пустого описания) добираются пачками по 100 через
    `POST /rest/api/3/issue/bulkfetch`. Недоступная задача отчёт не ломает: вместо ключа в строке
    останется `issue #<id>`. Записи одного человека тянет `/4/worklogs/user/{accountId}` — запрос на
    человека, а не общий `/4/worklogs`: детально отслеживаемых единицы, и качать ради них worklog'и
    всего инстанса незачем.
11. **Внешний OAuth Forge не работает в фоне.** `providers.auth` + `api.asUser().withProvider(...)`
    доступны только там, где есть пользователь в сессии; `asApp()` с внешними провайдерами не
    поддерживается, а `scheduledTrigger` и консьюмер очереди выполняются без пользователя. Поэтому
    Slack подключается своим OAuth-потоком, а токен живёт в секретном хранилище (см.
    [«Подключение Slack»](#подключение-slack)).
12. **Веб-триггер никем не аутентифицирован** и адрес его свой у каждой установки. Первое значит,
    что проверять звонящего обязано само приложение (одноразовый nonce из KVS); второе — что этот
    адрес нельзя зарегистрировать в Slack как `redirect_uri`, отсюда статическая страница-переходник.
13. **Переменные окружения Forge применяются только следующим деплоем**: `forge variables set` без
    `forge deploy` ничего не меняет в работающем приложении. И они привязаны к окружению — значения
    для `development` и `production` задаются раздельно.
14. **Установка на всю организацию (Enterprise Grid) не проверялась.** Токен такой установки
    приложение сохранит (в записи о подключении останется `isEnterpriseInstall: true`), но часть
    методов Slack для org-wide токенов требует явного `team_id`, которого приложение не передаёт.
    Пока безопасный путь — ставить приложение в конкретный workspace.
