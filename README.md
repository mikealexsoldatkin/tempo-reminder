# Forge-приложение: напоминание в Slack о незалогированном времени

Приложение сверяет **явно выбранный список пользователей Jira** с worklog'ами Tempo и шлёт **DM в Slack**
тем, у кого нет записей **за каждый** из последних N рабочих дней. Всё настраивается через UI —
**env-переменные не используются**.

## Что где лежит

| Файл | Назначение |
| --- | --- |
| `manifest.yml` | модули (adminPage, scheduledTrigger, consumer, function), scopes, egress-домены |
| `src/index.js` | точки входа: резолвер страницы, плановый триггер, консьюмер очереди |
| `src/backend/store.js` | всё состояние в Forge KVS, токены — в секретном хранилище |
| `src/backend/reminder.js` | сам прогон проверки |
| `src/backend/workdays.js` / `holidays.js` | окно рабочих дней и календарь праздников (правила → даты) |
| `src/backend/dailyReport.js` | детальный отчёт: разбор окна по дням для Detailed tracking users |
| `src/backend/vacations.js` / `ics.js` | матчинг событий календаря на людей и разбор iCal-фида |
| `src/backend/vacationCalendar.js` | загрузка календаря отпусков и проверка подключения |
| `src/backend/jira.js` / `tempo.js` / `slack.js` | интеграции |
| `src/frontend/admin.jsx` | страница настроек (UI Kit) |
| `test/` | тесты окна рабочих дней, отпусков, разбора iCal, детального отчёта и отбора проектных ролей (`npm test`) |

## Страница настроек

Jira → **Настройки** → **Приложения** → **Tempo Reminders**. Доступна только администраторам Jira
(резолверы дополнительно проверяют право `ADMINISTER` — adminPage лишь прячет пункт меню).

### 1. Вкладка «Users»
Вместо прежнего `getProjectPeople()` список отслеживаемых людей задаётся вручную:

- **Поиск по имени** — вводите First + Last name (Jira ищет и по email), отмечаете нужных
  галочками и добавляете **батчем**.
- **Добавить участников проекта** — по ключу проекта подтягивает людей из **собственных ролей
  проекта**, то есть ровно то, что видно в Project settings → People. Общие (инстансные) роли
  игнорируются. Ещё не отслеживаемые отмечаются автоматически, в таблице видно, из какой роли
  пришёл человек.
- **Таблица отслеживаемых** — удаление по одному и батчем, плюс ручная правка email.

Отмеченных в любом из двух поисков можно отправить в **три независимых списка** — кнопками
**«Track»** (Tracked users), **«Track in detail»** (Detailed tracking users) и
**«Mark as a manager»** (Managers). Списки не связаны: один человек может быть в любых из них
или ни в одном, и в таблице результатов видно, где он уже есть.

#### Detailed tracking users

Отдельная таблица под Tracked users. По этим людям менеджеру уходит не «отчитался / не отчитался»,
а **разбор дня за днём** — что списано в Tempo по каждой задаче:

```
2026-08-10:
- 5.5h - ABC-123: [Development] Переписал импортёр
- 1h - ABC-140: [Meetings] Планирование спринта
2026-08-11:
- no time entries
2026-08-12:
- Independence Day — a holiday
```

`[Type of work]` в скобках — это **work attribute** записи в Tempo (в ответе API он приходит в
`attributes.values`). Атрибутов у записи может быть несколько — тогда они перечисляются через
запятую; если их нет вовсе, скобок в строке не будет. Пустое описание worklog'а заменяется
заголовком задачи. Первым в строке идёт списанное время в часах: дробное округляется до сотых
и пишется без хвостовых нулей (`1.5h`, `0.25h`, `8h`).

Устройство:

- **Колонка «Managers who get the report»** — кто получает отчёт. Пока она пуста, отчёт не уходит
  никому, и прогон честно пишет об этом в таблице последнего прогона. Выбирать можно только из
  таблицы Managers; удаление менеджера снимает его и отсюда, и из Tracked users.
- **Одно сообщение — один сотрудник.** Сшивать нескольких в одно письмо значило бы отправить
  менеджеру простыню, в которой ничего не найти.
- **Email и Slack в таблице не показываются**: сообщение получает менеджер, а от самого сотрудника
  нужен только accountId для запроса в Tempo.
- **Окно — целиком «Working days to check»**, без скидки на «Acceptable days of delay»: менеджер,
  который смотрит человека глубоко, хочет видеть и сегодняшний день. Пустой день оправдывают только
  выходной, праздник и календарь отпусков, и причина печатается прямо под датой — пустая строка
  неотличима от «приложение недосчиталось записей».
- **Расписание — то же, что у «Manager run times»**, отдельного поля нет. Но по выходным детальные
  отчёты не уходят, даже если галочка «Don't run the scheduled check on weekends» снята. Ручной
  запуск с вкладки «Run check» это правило игнорирует, как и остальные.
- **Отпуск ищется и по этому списку тоже.** Если человека нет в Tracked users, «Name in the vacation
  calendar» задать ему негде и в календаре он ищется по displayName из Jira. Когда написание в
  календаре расходится с Jira, добавьте его ещё и в Tracked users — override берётся оттуда.

> **Про email.** Slack ищется по email, а приложению видны только профильные поля с видимостью
> **«Anyone»**. Email обычно стоит «Only people in your organization»: коллега видит его в профиле,
> приложение — нет. Поэтому адреса берутся через Email API (`/rest/api/3/user/email/bulk`), который
> отдаёт их независимо от видимости; он требует scope `read:email-address:jira` и в Forge работает
> **только через `asApp()`**. Если адреса нет и там, в таблице будет «set an email» — впишите вручную.
> Найденный Slack-id кэшируется, чтобы не звать `users.lookupByEmail` каждый прогон.

### 2. Вкладка «Access tokens»
- **Tempo API token** и **Slack bot token** — password-поля. Значения кладутся в секретное хранилище
  Forge (`kvs.setSecret`) и наружу **никогда не возвращаются**: UI видит только «set / not set»,
  последние 4 символа и дату обновления. Где их взять — в разделе [«Где взять токены»](#где-взять-токены).
- **Test connection** — дёргает Tempo и Slack `auth.test` текущими токенами.

### 3. Вкладка «Check parameters»
- Параметры проверки:
  - **Working days to check** — всё окно: последние N рабочих дней, включая сегодняшний;
  - **Acceptable days of delay** — сколько самых свежих рабочих дней окна прощаем (время за них
    ещё могут не успеть занести). Значение всегда меньше окна, чтобы хотя бы один день спрашивался.
- **Логика проверки:** время должно быть залогировано **за каждый** рабочий день окна по отдельности,
  а не «хоть за какой-нибудь». Спрашиваемые дни = окно минус допустимая задержка: при 5 и 1 прогон
  проверяет 4 рабочих дня до сегодняшнего. Достаточно одного дня без записей, чтобы человеку ушло
  напоминание; в сообщение подставляется список именно пропущенных дней.
- Ещё параметры: времена запуска двух рассылок и четыре шаблона сообщений (сотруднику,
  менеджеру-дайджест, детальный отчёт, менеджеру «все отчитались») с плейсхолдерами `{name}`,
  `{from}`, `{to}`, `{days}`, `{missing}`, `{missingCount}`, `{count}`, `{list}`, `{user}`,
  `{report}`. Всё сохраняется кнопкой **«Save settings»**; пропуск выходных и праздников переехал
  на вкладку «Holidays».
- **Manager run times** — одно расписание на всё, что уходит менеджерам: дайджесты, «все
  отчитались» и детальные отчёты. Отдельного поля под последние нет намеренно — они и есть часть
  менеджерской рассылки, просто не уходят по выходным.
- В шаблоне детального отчёта `{name}` — имя **получателя** (менеджера), `{user}` — тот, о ком
  отчёт, `{report}` — сам разбор по дням. Подстановка идёт за один проход, поэтому `{days}`,
  случайно оказавшийся в описании worklog'а, числом не станет.

### 4. Вкладка «Holidays»
Сверху — две галочки, определяющие, какие дни считаются нерабочими: **«Don't run the scheduled check
on weekends»** и **«Take the holiday calendar into account»**. Обе сохраняются сразу, без отдельной
кнопки. С выключенным календарём список ниже ни на что не влияет — праздники становятся обычными
рабочими днями.

Сам календарь: праздник — не рабочий день, поэтому в окно проверки он не попадает и планового
прогона в этот день нет.

Праздники хранятся **правилами**, а не датами, иначе календарь пришлось бы переписывать каждый год:

| Тип | Что задаёт | Пример |
| --- | --- | --- |
| `fixed` | одно и то же число каждый год | 1 января, 25 декабря |
| `nth-weekday` | N-й день недели месяца (N < 0 — с конца) плюс сдвиг в днях | последний понедельник мая |

Сдвиг нужен для дней, привязанных к другому празднику: пятница после Дня благодарения — это
«4-й четверг ноября + 1 день», а **не** «4-я пятница ноября»: в годы, где 1 ноября приходится на
пятницу (например, 2030-й), это разные даты.

Набор по умолчанию: Новый год (1 января), православное Рождество (7 января), День Победы (9 мая),
Memorial Day (последний понедельник мая), Independence Day (4 июля), Labor Day (первый понедельник
сентября), Thanksgiving (4-й четверг ноября) и следующий за ним день, католическое Рождество
(25 декабря). Кнопка **«Restore defaults»** возвращает этот список.

### 5. Вкладка «Vacations»

Отпуск — это **не долг**: день, который человек провёл в отпуске, вычёркивается из его пропущенных,
поэтому о нём не спрашивают ни самого сотрудника, ни его менеджера. Если отпуск закрыл все
спрашиваемые дни, человек не получит ничего и в дайджест менеджера не попадёт.

Логика **подневная**, а не «человек в отпуске — выключаем целиком». Вернувшийся из двухнедельного
отпуска не получит претензию за дни своего отсутствия, но за уже отработанные дни окна — получит.
В отличие от праздника, отпуск не меняет ни само окно рабочих дней, ни решение «запускать ли прогон
сегодня»: он персональный.

Две галочки, обе сохраняются сразу:

- **«Take the vacation calendar into account»** — учитывать календарь вообще;
- **«Don’t message a person while they are on leave…»** — если человек в отпуске **сегодня**, но за
  более старые дни окна долг есть, DM придерживается до его возвращения. В дайджест менеджеру он
  при этом попадает, чтобы дни не потерялись.

**Доступ к календарю.** Приложение читает корпоративный календарь отпусков по ссылке
**«Secret address in iCal format»** (Google Calendar → нужный календарь → Settings → Integrate
calendar). Ни OAuth, ни сервисного аккаунта, ни проекта в GCP не требуется — что важно, если
доступа к GCP у администратора нет. Ссылка сама себе пароль, поэтому лежит в том же секретном
хранилище, что и токены, и наружу не отдаётся: в UI видно только id календаря и дату обновления.

> **Про задержку.** Этот фид Google отдаёт из кэша, так что отпуск, добавленный HR только что,
> приложение увидит не сразу (обычно в пределах нескольких часов). Для отпусков, которые заводят
> заранее, это приемлемо; если однажды станет мешать, менять придётся только
> `vacationCalendar.js` — остальное от способа доступа не зависит.

**Как события связываются с людьми.** Событие считается отпуском, если в его заголовке встретилось
имя отслеживаемого сотрудника: `[vacation] Aleksandr Bugrov`. Тег в начале роли не играет — в этом
календаре любое событие означает, что человека нет на работе. Сравнение не различает регистр,
диакритику и пунктуацию, но идёт **по границам слов**, иначе «Ann Lee» находилась бы внутри
«Joann Leeson». Учитываются только события **на весь день**; события со временем и повторяющиеся
(`RRULE`) в отпуска не идут — последние считаются отдельно и попадают в предупреждение, чтобы не
пропасть молча.

Если в календаре человека пишут иначе, чем в Jira (никнейм, другой порядок слов, кириллица),
впишите это написание в колонку **«Name in the vacation calendar»** на вкладке Users; несколько
вариантов — через запятую.

**Test connection** отвечает не только «читается / не читается»: он показывает ближайшие события с
пометкой, кто из отслеживаемых в них узнан, и отдельным списком — заголовки, не сматчившиеся ни с
кем. Это единственный способ заметить разошедшееся написание имени до того, как напоминание уйдёт
человеку в отпуске.

**Если календарь не ответил**, прогон не останавливается: отпуска просто не учитываются, а причина
попадает в отчёт предупреждением. Остаться без напоминаний из-за недоступности Google хуже, чем
один раз дёрнуть отпускника; молчать об этом нельзя, потому что «отпусков нет» иначе не отличить
от «календарь не прочитался».

### 6. Вкладка «Run check»
Кнопка **«Start check»** запускает тот же прогон, что и расписание, но немедленно и в обход
`scheduledTrigger`. Ограничения «выходной» и «раз в день» на ручной запуск не действуют. Перед отправкой
показывается подтверждение — уходят **реальные** сообщения в Slack. Ниже — отчёт последнего прогона
(кто залогировал, кому ушло напоминание, кто был в отпуске, где ошибка), а под ним — что ушло
менеджерам: дайджесты и детальные отчёты строкой на пару «сотрудник — получатель».

Прогон выполняется не в резолвере, а в **очереди** (`@forge/events`): у резолвера лимит ~10 секунд,
а Tempo и Slack приходится опрашивать с паузами. Поэтому UI поллит статус, пока job в работе.

## Где взять токены

Оба токена вводятся на вкладке **«Access tokens»** страницы настроек приложения и попадают
в секретное хранилище Forge (`kvs.setSecret`). Обратно в UI они не отдаются: видно только
«set / not set», последние 4 символа и дату обновления. После сохранения обоих нажмите
**Test connection** — приложение дёрнет Tempo и Slack `auth.test` текущими значениями.

### Tempo API token

1. В Jira откройте **Apps → Tempo**, затем в левом меню Tempo — **Settings** (шестерёнка внизу).
2. Раздел **API integration** → кнопка **New Token**.
3. Заполните:
   - **Name** — понятное имя, например `Tempo Reminder (Forge)`;
   - **Expiration** — срок жизни токена (после истечения прогон начнёт падать с ошибкой
     `Couldn't fetch worklogs from Tempo`, токен придётся выпустить заново);
   - **Scope / доступ** — достаточно **чтения worklog'ов** (`View worklogs` / read-only).
     Права на запись приложению не нужны.
4. Нажмите **Create** и **сразу скопируйте значение** — Tempo показывает токен один раз.
5. Вставьте его в поле **Tempo API token** и нажмите **Save**.

> Токен работает от имени того, кто его создал: этот человек должен видеть worklog'и **всех**
> отслеживаемых сотрудников (обычно это Tempo-администратор). Иначе часть людей окажется
> «не отчитавшимися» просто потому, что их записи не видны токену. По той же причине токен,
> выпущенный увольняющимся сотрудником, лучше перевыпустить заранее.

### Slack bot token

В качестве Slack-бота используется уже созданное приложение **«Tempo Reminder»** в workspace
`americor.slack.com` — новое создавать не нужно (но если сильно хочется, или потеряется доступ, то можно):

**<https://americor.slack.com/marketplace/A0BL9AG1SHZ-tempo-reminder?settings=1>**

1. Откройте ссылку выше — это страница приложения в workspace (настройки, доступ, кто установил).
   Нужны права администратора workspace либо роль collaborator у приложения.
2. Сам токен лежит в консоли разработчика: **<https://api.slack.com/apps>** → приложение
   **Tempo Reminder** → **OAuth & Permissions** → **Bot User OAuth Token** вида `xoxb-…`.
3. Проверьте, что в **Scopes → Bot Token Scopes** есть все четыре:

   | Scope | Зачем |
   | --- | --- |
   | `users:read` | базовый доступ к справочнику пользователей |
   | `users:read.email` | поиск сотрудника по email (`users.lookupByEmail`) |
   | `chat:write` | отправка сообщения |
   | `im:write` | открытие личного канала с сотрудником |

   Если какого-то scope не хватает — добавьте и переустановите приложение в workspace
   (**Install App → Reinstall to Workspace**); после переустановки **значение `xoxb-…` меняется**,
   и его нужно обновить в настройках приложения.
4. Вставьте токен в поле **Slack bot token (xoxb-…)** и нажмите **Save**.

> Бот пишет только в личку (DM), приглашать его в каналы не нужно. Чтобы найти человека в Slack,
> приложению нужен его **email** — тот же адрес, что в Jira. Если адреса нет, в таблице
> отслеживаемых будет «set an email»: впишите его вручную, иначе сотрудник получит статус
> `no email` и сообщение ему не уйдёт.

## Установка и деплой

```bash
npm install
forge deploy
forge install     # выбрать Jira и указать сайт
```

Если приложение уже установлено, а в `manifest.yml` добавились scope'ы, после `forge deploy`
обязателен **`forge install --upgrade`**: новые права требуют подтверждения администратором,
и до апгрейда приложение работает со старым набором scope'ов.

Токены и список пользователей **не задаются через CLI** — только на странице настроек после установки.

## Как проверить

- **Из UI** — кнопка «Start check», результат сразу в отчёте под ней.
- **Локально** — `npm test` (расчёт окна рабочих дней), `forge lint`, `forge tunnel` + `forge logs`.

## Известные подводные камни

1. **Нет cron** у scheduledTrigger — только `fiveMinute | hour | day | week`. Стоит `day`; выходные,
   праздники и окно рабочих дней считаются в коде (`src/backend/workdays.js`, `holidays.js`), защита
   от повторной рассылки — настройка «не повторять за день». Время запуска — UTC, и даты праздников
   разворачиваются в том же UTC.
2. **Приложение не видит email в профиле.** Forge-приложениям доступны только поля с видимостью
   «Anyone», поэтому `/user/search` и `/user/bulk` возвращают `emailAddress` далеко не всегда —
   даже когда вы сами видите адрес в профиле сотрудника. Читаются адреса через Email API
   (`/user/email/bulk`, scope `read:email-address:jira`, только `asApp()`). Scope в статусе Beta.
3. **Egress**: любой внешний домен обязан быть в `permissions.external.fetch.backend`, иначе `fetch`
   отклонят (`REQUEST_EGRESS_ALLOWLIST_ERR`). `api.tempo.io` и `slack.com` уже прописаны.
4. **Rate limits**: Tempo режет на ~5 req/s — worklog'и тянутся одним пагинированным запросом на всё
   окно с ретраями на 429/5xx; между вызовами Slack стоят паузы.
5. **Размер значения в KVS** ограничен, поэтому отчёт о прогоне обрезается до 300 строк
   (сначала ошибки и пропуски); полный список — в `forge logs`.
6. `scheduledTrigger` стартует примерно через 5 минут после первого деплоя/установки.
7. **`@forge/events` v2+ сменил контракт консьюмера**: вместо `resolver: {function, method}` в
   манифесте пишется `function:`, а хендлер — обычная `export async function handler(event)`,
   где тело лежит в `event.body`. Старая форма **всё ещё проходит `forge lint`**, но рантайм
   отклоняет `queue.push()` с `400 Bad Request` без пояснений.
8. **Участники проекта берутся из ролей, а не из `/user/assignable/search`.** Тот эндпоинт отдаёт
   всех, у кого есть право «Assignable User»; если оно выдано на «Any logged in user», возвращается
   весь инстанс. При этом `/project/{key}/role` возвращает и общие роли инстанса, поэтому берём
   только те, у которых `scope.type === 'PROJECT'` (собственные роли проекта). Если своих ролей нет
   вовсе — это company-managed проект, где все роли общие и при этом и есть People, и тогда берём
   все. Группы внутри ролей разворачиваются через устаревший `/rest/api/3/group?expand=users`:
   актуальный `/rest/api/3/group/member` требует scope `manage:jira-configuration` — право на изменение
   конфигурации Jira, непропорциональное для read-only приложения. Если Atlassian уберёт устаревший
   эндпоинт, альтернатива — добавить этот scope и перейти на `group/member`.
9. `"type": "module"` в package.json заставляет webpack считать наш код строгим ESM, из-за чего
   default-импорт CJS-пакета связывается со всем `module.exports`. Поэтому резолверы собираются
   через именованный `makeResolver()`, а не через `new Resolver()` (иначе — `out is not a constructor`).
10. **В worklog'е Tempo нет ключа задачи** — только числовой `issue.id` Jira. Для детального отчёта
    ключи (и заголовки, чтобы подставить их вместо пустого описания) добираются пачками по 100 через
    `POST /rest/api/3/issue/bulkfetch`. Недоступная задача отчёт не ломает: вместо ключа в строке
    останется `issue #<id>`. Записи одного человека тянет `/4/worklogs/user/{accountId}` — запрос на
    человека, а не общий `/4/worklogs`: детально отслеживаемых единицы, и качать ради них worklog'и
    всего инстанса незачем.
